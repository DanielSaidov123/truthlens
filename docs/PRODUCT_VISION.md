# TruthLens — Product Vision & Goals

**Status:** Draft (KAN-10)  
**Stage:** Product discovery (Epic KAN-4)  
**Owner:** TruthLens team  
**Last updated:** Stage 3 (Database & Job Queue)  
**Language/UI:** Hebrew, RTL (future Android/iOS via shared backend)

This document defines what TruthLens does, for whom, and how success is measured.
It complements `README.md` and `docs/ARCHITECTURE.md` and must not contradict them.
It does not introduce new technology or change product code.

---

## 1. Problem

Users increasingly encounter videos that may have been generated or altered by AI.
Today they have no simple, trustworthy way to obtain an **evidence-based assessment**
of whether a video looks AI-generated or AI-edited.

Key pain points:

- It is hard to tell real footage from synthetic or heavily edited footage by eye.
- Existing tools often present a single opaque score with no explanation.
- Users (journalists, researchers, moderators, and the general public) need a
  cautious assessment, not an absolute verdict.
- Hebrew/RTL users are underserved by most existing tools.

TruthLens addresses this by producing a structured, evidence-based evaluation with
clear limitations, rather than claiming certainty.

## 2. Vision

TruthLens is a web-first service that helps users assess whether a video was
likely generated by AI or edited with AI, and explains the basis for that
assessment.

Core vision statement:

> Give users a cautious, evidence-based second opinion on video authenticity,
> in Hebrew, without pretending to know the truth with certainty.

Longer term (not MVP): mobile clients (Android/iOS) on the same backend, plus
additional input types and deeper forensic signals.

## 3. Target audience

Primary (MVP):

- Hebrew-speaking users who need to evaluate a video's authenticity.
- Journalists, researchers, moderators and analysts who review user-generated
  or third-party video.
- General users who want a second opinion before sharing or trusting a video.

Secondary (later):

- Organizations that need audit trails and history of checks.
- Mobile users (Android/iOS) — future, via shared backend.

Assumption (open question): exact audience segments and their relative priority
are not yet validated by user research. This document treats them as initial
hypotheses.

## 4. Core value proposition

- **Evidence, not certainty:** results are framed as an assessment with
  limitations (`inconclusive` when evidence is insufficient).
- **Explainability:** findings reference time ranges and evidence, not only a score.
- **Hebrew/RTL first:** native Hebrew experience.
- **Shared backend:** designed so mobile clients can reuse the same API later.
- **Cautious AI honesty:** `provider = "mock"` in Stage 3 is never presented as a
  real model verdict.

## 5. Main use cases (MVP)

The following are **planned MVP targets**. In Stage 3 the upload API and frontend
flows are not yet implemented; the queue/worker pipeline exists and processes jobs
created directly (e.g. for testing). These use cases describe the intended product
behaviour for Stage 4+.

1. **Upload a file (planned)** — user selects a local video; system validates input
   and creates an analysis job; user sees progress and a result.
2. **Submit a link (planned)** — user provides a URL from a supported source;
   system validates and creates an analysis job.
3. **View result** — user sees verdict, confidence (only when grounded), findings
   with time ranges, limitations, and timestamps.
4. **Understand limitations** — user is told clearly what the system cannot
   determine and when the result is `inconclusive`.

Out of scope for MVP (see KAN-11): native mobile apps, payments/subscriptions,
social sharing, full user accounts, unless an approved requirement exists.

## 6. Product principles

1. **Cautious honesty:** never claim 100% certainty; use `inconclusive` when
   evidence is insufficient.
2. **Evidence-based:** every verdict is backed by findings with time ranges and,
   where available, evidence references.
3. **Hebrew/RTL first:** all user-facing text and layout are Hebrew/RTL.
4. **Simple and focused:** minimal scope; avoid features not required for MVP.
5. **Modular and extensible:** keep the API reusable for future mobile clients.
6. **Security and privacy by default:** no secrets, private videos, or sensitive
   data in logs; clear data lifecycle (KAN-16).
7. **Provider independence:** analysis is behind a contract; mock results are
   never presented as real.

## 7. Measurable goals (KPIs)

Targets are intentionally defined as measurement definitions; numeric targets
are **not fixed** here because no baseline exists yet. Numeric goals must be set
after initial usage data (assumption/open question).

1. **Successful analysis rate** — share of started analyses that reach
   `completed` successfully.
2. **Failure rate** — share of started analyses that end in `failed`, broken
   down by error code (e.g. `INVALID_MEDIA`, `TIMEOUT`, `OBJECT_MISSING`).
3. **Time to result** — elapsed time from job creation to `completed` (p50/p95),
   measured per provider and file size.
4. **Result completeness** — share of completed results that are structurally
   complete (at least one finding, or an explicit `inconclusive` verdict with
   limitations; no empty results).
5. **User understanding (optional)** — share of users who report the result was
   understandable. Requires a feedback mechanism not yet implemented.

Open question: whether to track a "user agrees with verdict" metric; requires a
feedback UI not in MVP.

## 8. General boundaries

- Web-first; mobile is a future goal via shared backend.
- No payments, subscriptions, or full account system in MVP.
- No claim of 100% AI detection accuracy.
- No real AI provider in Stage 3; the worker uses `provider = "mock"`.
- Upload API and frontend flows are later stages (Stage 4+), pending approval.
- Data retention and deletion are defined in `docs/DATA_LIFECYCLE.md` (KAN-16).

## 9. Assumptions and open questions

1. **Audience priority** is an initial hypothesis; needs user research.
2. **Numeric KPI targets** require baseline data; to be set after first usage.
3. **Supported input formats and size limits** are not yet defined (KAN-11/KAN-12).
4. **Result schema** (verdicts, confidence, findings) was defined in KAN-15: the contract
   verdicts (`likely_ai_generated`, `possible_ai_edit`, `no_clear_ai_evidence`,
   `inconclusive`) are mapped to the existing `Verdict` enum in
   `backend/prisma/schema.prisma` (`ai_generated`, `ai_edited`, `likely_real`,
   `inconclusive`) for persistence.
5. **Privacy/legal review** is required before public launch (KAN-16).
6. **Abandonment rate** is a future operational metric, only if it can be measured
   reliably (requires tracking started analyses that never reach a terminal
   status). It is not a core KPI for the MVP.
7. **AI provider selection** is out of scope for Stage 3 (mock only).
